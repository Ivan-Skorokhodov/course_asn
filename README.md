# CAIDA AS Relationships → CSR и фильтрация по списку ASN

Проект преобразует исходные отношения автономных систем из **CAIDA AS Relationships serial-2** в разреженный ориентированный граф CSR (SciPy), а затем при необходимости строит **индуцированный подграф** по заданному списку ASN. Исходный полный граф остаётся неизменным.

Текущая версия не реализует AS Rank, PeeringDB/IXP, визуализацию, моделирование BGP-маршрутизации или ACO. Фильтрация выполняется **по готовому текстовому списку ASN**, без внешних API.

## 1. Подготовка окружения

Команды выполняются из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Основные зависимости: NumPy и SciPy. Формат входного CAIDA-файла — обычный `.txt` или сжатый `.gz`.

## 2. Построение полного графа CAIDA

```bash
python -m src.graph build \
  data/raw/20261101.as-rel2.txt \
  --out data/processed

python -m src.graph inspect --dir data/processed
```

В исходном файле serial-2 каждая запись содержит `asn1|asn2|relationship|source`:

| Значение relationship | Отношение | Дуги в CSR |
|---|---|---|
| `-1` | `asn1` — провайдер `asn2` | `asn1 → asn2` (`DOWNSTREAM=2`), `asn2 → asn1` (`UPSTREAM=1`) |
| `0` | Peering | Две встречные дуги (`PEER=3`) |

Одна физически не подтверждённая, *выведенная CAIDA* связь AS представляется двумя направленными дугами. В `graph.npz` значение `1` означает наличие дуги, **не задержку и не стоимость маршрута**. Поле `source` (`bgp`/`mlp` и т. п.) текущий CSR не сохраняет.

## 3. Построение подграфа по списку ASN

Файл `data/raw/asn-2026-11-26` содержит **36 302 уникальных числа**, одно в строке. В частности, в нём встречается `0`: парсер списка его допускает, но номер отсутствует в полном CAIDA-графе и учитывается как отсутствующий при фильтрации.

Запуск:

```bash
python -m src.graph filter \
  --asns data/raw/asn-2026-11-26 \
  --dir data/processed \
  --out data/filtered

python -m src.graph inspect --dir data/filtered
cat data/filtered/metadata.json
```

**Правило отбора:** оставляем пересечение списка ASN с вершинами исходного CAIDA и **только те исходные отношения, у которых оба конца остались**. Это индуцированный подграф: новые связи не создаются; отношения через исключённые AS не восстанавливаются; изолированные выбранные AS остаются в наборе вершин.

Результат записывается **отдельно** в `data/filtered/` и не перезаписывает `data/processed/`.

### Фактический результат фильтрации

Данные из `data/filtered/metadata.json`, присланные после локального запуска:

| Метрика | Полный CAIDA | После фильтрации | Сохранено |
|---|---:|---:|---:|
| Вершины (AS) | 81 623 | **36 006** | **44,11%** |
| Направленные дуги | 1 360 356 | **830 414** | **61,04%** |
| Уникальные AS-отношения | 680 178 | **415 207** | **61,04%** |
| Provider–customer отношения | 171 391 | **80 144** | **46,76%** |
| Peering отношения | 508 787 | **335 063** | **65,86%** |

Дополнительная статистика:

| Метрика | Результат |
|---|---:|
| ASN в исходном списке | 36 302 |
| Отсутствуют в исходном CAIDA | **296** |
| Изолированные AS в новом графе | **666** (1,85% вершин) |
| Сохранённые дуги `upstream` | 80 144 |
| Сохранённые дуги `downstream` | 80 144 |
| Сохранённые дуги `peer` | 670 126 |
| Удалено отношений через границу отбора (один конец вне списка) | 237 756 |
| Удалено отношений, оба конца которых вне отбора | 27 215 |

Контрольная сумма отношений: `415207 + 237756 + 27215 = 680178`.

**Интерпретация изоляции:** 666 AS присутствуют в фильтрованном наборе вершин, но не имеют в нём ни одного соседа. Они **не обязательно изолированы в полном CAIDA**: их связи могли вести только к исключённым AS. В исходном CSR каждая вершина участвовала хотя бы в одном отношении; поэтому эти 666 AS потеряли все свои наблюдаемые связи именно из-за фильтрации. Внутри фильтрованного графа от них нельзя построить путь к другой AS. **Это не доказательство отсутствия маршрута в реальном Интернете.**

Пока **не измерены** число компонент слабой связности, размер крупнейшей компоненты и достижимость конкретных AS внутри нового графа. Высокая доля сохранённых рёбер сама по себе этого не гарантирует.

## 4. Сохранённые файлы и метаданные

Обе директории (`processed/` и `filtered/`) используют один формат `csr_aligned_v1`:

| Файл | Назначение |
|---|---|
| `graph.npz` | CSR-матрица смежности, размер `N × N` |
| `edge_types.npy` | Типы направленных дуг **строго в порядке `graph.indices`** |
| `asn_ids.npy` | Отсортированные реальные ASN, соответствующие индексам вершин |
| `metadata.json` | Статистика и происхождение построенного графа |

Для `data/filtered/metadata.json` записываются `operation=induced_subgraph_by_asn_list`, `format=csr_aligned_v1`, время сборки, `input_sha256`, `asn_list_sha256`, пути и размеры исходного CSR, `requested_asns`, `found_asns`, `missing_asns_count`, сами `missing_asns`, типы и числа отношений, `boundary_relationships_removed`, `outside_outside_relationships_removed`, `isolated_vertices`.

Файлы не содержат полных BGP-таблиц, географии или IP-трафика. Метаданные сохраняют SHA-256 исходных данных, но **не** заменяют сами исходные файлы.

## 5. Ограничения

- CAIDA восстанавливает отношения из ограниченных наблюдений BGP/других источников; отсутствие ребра не доказывает отсутствия реального соединения, включая private peering.
- Одной паре AS присваивается один тип отношений; реальная BGP-политика может различаться по локации, префиксу, времени и направлению.
- `bgp` и `mlp` в serial-2 указывают на происхождение вывода об отношении; текущий CSR их не сохраняет. `mlp` не равен доказанной прямой двусторонней BGP-сессии.
- Фильтрация дополнительно удаляет отношения к невыбранным AS и может уничтожить реальные пути между оставшимися AS.
- Наличие пути в CSR не гарантирует BGP-достижимости по этому пути: маршрутизация и коммерческие политики здесь не моделируются.
