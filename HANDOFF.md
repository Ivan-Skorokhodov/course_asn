# Handoff — CAIDA serial-2 → полный CSR → подграф по списку ASN

**Актуализировано: 27 ноября 2026 года.** Описание составлено по последнему доступному `src/graph.py` из `Ivan-Skorokhodov/course_asn` и результатам локального запуска пользователя. Значения для фильтрованного графа — **наблюдённые результаты**, а не повторные вычисления в этой среде.

## 1. Актуальная задача и границы

Текущий pipeline выполняет только две операции:

1. Построение **полного** типизированного ориентированного AS-графа из CAIDA AS Relationships `serial-2`, сохранённого в CSR.
2. Создание **индуцированного подграфа** по локальному списку ASN с сохранением только исходных отношений между выбранными AS.

Оба этапа воспроизводимы по исходным файлам; оба сохраняют JSON-метаданные. **Исходный CSR не изменяется при фильтрации**.

В текущей версии **нет** AS Rank, Customer Cone, PeeringDB/IXP, ACO, моделирования DNS-anycast, выбора целевых AS, функции качества, расчёта BGP-маршрутов и визуализаций. Список `asn-2026-11-26` используется как готовый вход: его происхождение и метод отбора в текущем коде не анализируются. Не возвращать старые алгоритмы и эвристики без отдельного решения пользователя.

## 3. Входные данные и формат отношений CAIDA

Исходный снимок: `data/raw/20261101.as-rel2.txt` (plain text; `.gz` также поддерживается).

Строка CAIDA serial-2: `asn1|asn2|relationship|source`.

- `asn1|asn2|-1|source`: `asn1` — provider, `asn2` — customer. Создать `asn1 → asn2` (`DOWNSTREAM=2`) и `asn2 → asn1` (`UPSTREAM=1`).
- `asn1|asn2|0|source`: peers. Создать две встречные дуги (`PEER=3`).

Парсер `read_relationships` не использует четвёртое поле `source`, пропускает пустые строки и `#`-комментарии, проверяет корректность основных трёх полей и запрещает петли. Дубли идентичных дуг удаляются; конфликтующие типы для одной направленной пары приводят к ошибке.

`data/raw/asn-2026-11-26`: текст с **36 302 уникальными числами**, по одному в строке. При чтении `read_asn_list` пропускает пустые строки, проверяет десятичную запись и дубликаты, сортирует номера. **ASN 0 принимается как число входного списка**, но отсутствует среди вершин исходного CAIDA: он учитывается в `missing_asns`, а не добавляется в граф. Отрицательные и выходящие за пределы 32-битного диапазона значения отклоняются.

## 4. Реализация `src/graph.py`

| Функция | Назначение |
|---|---|
| `open_text` | Чтение `.txt` / `.gz` |
| `read_relationships` | Парсинг строк CAIDA и создание двух направленных дуг на отношение |
| `build_graph` | Сортировка ASN и дуг, проверка конфликтов, дедупликация и построение CSR |
| `save_graph` | Сохранение полного CSR и JSON-метаданных с SHA-256 источника |
| `load_graph` | Загрузка CSR, массивов типов дуг и ASN |
| `read_asn_list` | Чтение списка ASN с валидацией |
| `induced_subgraph` | Пересечение множества вершин и сохранение только дуг между оставшимися |
| `filter_graph` | Подграф, статистика потерь, сохранение файлов и JSON |
| `main` | CLI-команды `build`, `filter`, `inspect` |

### 4.1. Контракт `csr_aligned_v1`

Файлы в обеих выходных директориях имеют одинаковое представление:

- `graph.npz` — SciPy CSR размера `N × N`, ненулевое значение равно `1` и означает наличие направленной дуги.
- `edge_types.npy` — типы дуг, синхронизированные с последовательностью элементов CSR (`indptr`/`indices`). **Нельзя сортировать `graph.indices` отдельно от `edge_types`.**
- `asn_ids.npy` — строго возрастающие ASN; индекс вершины `i` соответствует `asn_ids[i]`.
- `metadata.json` — происхождение, формат, размеры и счётчики.

В `induced_subgraph` для фильтрации временно создаётся CSR, в данных которого лежат *коды типов*. SciPy вырезает нужные строки и столбцы, после чего типы извлекаются из `subset.data`, а значения итогового `graph.npz` снова делаются равными `1`. Это сохраняет правильное соответствие дуг и типов даже при переупорядочивании CSR.

**Никаких новых отношений не добавляется; изолированные выбранные вершины сохраняются.**

### 4.2. Метаданные

Полный граф содержит `input_filename`, `input_sha256`, `built_at_utc`, `format`, размеры, счётчики типов связей и `type_codes`.

Фильтрованный граф дополнительно содержит:

- `operation=induced_subgraph_by_asn_list`;
- `source_graph_dir`, `source_graph_vertices`, `source_graph_directed_arcs`, `source_graph_relationships`;
- `asn_list_filename`, `asn_list_sha256`, `requested_asns`, `found_asns`, `missing_asns_count`, `missing_asns`;
- `n_vertices`, `n_directed_arcs`, `n_unique_as_relationships`, `provider_customer_relationships`, `peer_relationships`, `directed_arc_types`, `type_codes`;
- `boundary_relationships_removed`, `outside_outside_relationships_removed`, `isolated_vertices`, `built_at_utc`.

Оба JSON пригодны для аудита происхождения данных. Время `built_at_utc` относится к запуску программы, а не к дате измерений CAIDA.

Разбиение исключённых отношений:

| Категория | Количество |
|---|---:|
| Одна AS внутри отбора, другая снаружи (`boundary_relationships_removed`) | 237 756 |

**Контрольные равенства:**

- `36006 + 296 = 36302` — запрошенные ASN = найденные + отсутствующие.
- `80144 + 335063 = 415207` — отношения внутри подграфа.
- `80144 + 80144 + 670126 = 830414` — число направленных дуг.
- `415207 + 237756 + 27215 = 680178` — все отношения исходного графа.

**Интерпретация:** отбор сохранил 44,11% вершин и 61,04% связей; доля peering внутри нового графа составляет около 80,70% (для полного около 74,80%). Это не означает сохранения 61% реальных маршрутов: маршруты зависят от структуры связей и политик BGP.

### 5.3. Что означают 666 изолированных вершин

`isolated_vertices` вычисляется по `np.diff(subgraph.indptr) == 0`, то есть по нулевой степени вершины в **фильтрованном CSR**. Поскольку каждый исходный ASN появился в полном CAIDA из отношений, все такие AS ранее имели хотя бы одного соседа. Их связи в фильтрованном графе исчезли, потому что в отбор не вошёл ни один их сосед.

Следствия:

- Для изолированной AS нет пути к **другой** вершине внутри фильтрованного графа.
- Это **не** означает отсутствие пути к ней в полном CAIDA и не доказывает отсутствие внешней связи в реальном Интернете.
- Изолированные AS намеренно не удаляются, чтобы отбор точно отражал входной список и можно было анализировать потери связности.
- Отсутствие изоляции не гарантирует путь к произвольной целевой AS: для этого необходимо отдельно проверить компоненты и достижимость.

**Пока не вычислены:** число компонент слабой связности, размер крупнейшей компоненты, число компонент сильной связности и достижимость какой-либо конкретной целевой ASN. Нельзя утверждать, что весь подграф соединён.

## 6. Команды воспроизведения

Из корня репозитория с установленными `numpy`, `scipy`:

```bash
# Сборка исходного графа (при необходимости)
python -m src.graph build data/raw/20261101.as-rel2.txt --out data/processed

# Проверка исходного CSR
python -m src.graph inspect --dir data/processed

# Фильтрация по списку ASN
python -m src.graph filter \
  --asns data/raw/asn-2026-11-26 \
  --dir data/processed \
  --out data/filtered

# Проверка отфильтрованного CSR и метаданных
python -m src.graph inspect --dir data/filtered
cat data/filtered/metadata.json
```

Если в текущем терминале stdout не виден, к Python-командам временно добавлять `1>&2` (и для `cat` аналогично).

При повторной фильтрации из тех же файлов итоговая топология и типы дуг должны совпасть; `built_at_utc` обновится. Для сравнимых запусков сохранять хеши входного CAIDA и ASN-списка.

### Контрольные проверки, которые стоит автоматизировать позднее

1. `len(asn_ids) == graph.shape[0] == graph.shape[1]`, `len(edge_types) == graph.nnz`.
2. Типы дуг только `1,2,3`, для каждой CAIDA-связи встречные дуги согласованы.
3. Все ASN подграфа входят в ASN-список и полный граф.
4. Каждая дуга подграфа существует в полном графе с тем же типом отношения.
5. Проверяется сохранность изолированных вершин и равенства счётчиков из раздела 5.
6. Для анализа маршрутов отдельно проверять компоненты и достижимость, не делать выводы лишь по `isolated_vertices`.

## 7. Ограничения данных и результата

### 7.1. CAIDA serial-2

- **Неполнота наблюдений:** Route Views/RIPE RIS и другие источники не видят все AS-соединения; private peering может попасть в AS_PATH, но не обязательно. Полнота таблицы префиксов у одного Tier 1 не означает полноты AS-графа.
- **Инференция отношений:** единый тип `provider–customer` или `peer` на пару AS — упрощение; реальные BGP-политики зависят от площадки, префикса, направления и времени.
- **Источник связи:** `bgp` отражает вывод из наблюдаемых BGP-путей; `mlp` — вывод из multilateral peering на IX с участием route servers. Нахождение сетей на одном IX не равно гарантии peering между ними.
- **Дополнительные измерения:** serial-2 исторически включал Ark traceroute; новые Ark-выводы прекратили добавлять в сентябре 2018 года.
- **Эвристики:** вывод отношений зависит от доступных наблюдений и методики CAIDA; связи не являются подтверждённым списком всех коммерческих договоров.

### 7.2. Собственные допущения проекта

- CSR не хранит исходное поле `source`; по `edge_types.npy` нельзя отделить связи `bgp` и `mlp`.
- Все отношения представляются двумя направленными дугами, но **произвольная последовательность таких дуг не обязательно является допустимым BGP-маршрутом**.
- `graph.npz` кодирует только смежность, без географии, RTT, пропускной способности или объёма трафика.
- Подграф **сохраняет исходные отношения между выбранными AS**, но удаляет все пути через внешние AS. Изолированность и достижимость зависят от границы отбора.
- Результаты подграфа не являются оценкой процента сохранённых реальных BGP-путей или достижимого DNS-трафика.

## 8. Текущий статус и ближайшие решения

**Работает:** чтение CAIDA, построение полного CSR, чтение текстового списка ASN, индуцированная фильтрация, сохранение типов дуг и двух наборов JSON-метаданных. Пользователь получил числовой результат фильтрации 36 302 ASN до 36 006 вершин и 415 207 отношений.

**Не решено / не входит в текущий этап:** поиск маршрутов, проверка связности компонент, восстановление выпавших транзитных AS, выбор целевых AS, функция качества, ACO и внешнее обогащение. Прежде чем двигаться к алгоритмам маршрутизации, разумно посчитать компоненты и понять, какие важные пути оборвались после фильтрации, но это отдельный согласуемый этап.
