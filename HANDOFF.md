# Handoff — минимальное ядро CAIDA serial-2 → CSR

**Актуализировано: 27 ноября 2026 года.** Этот документ фиксирует состояние после сознательного упрощения проекта (*pivot*). Предыдущие эксперименты с AS Rank, PeeringDB, подграфами, географией и ACO **не входят в текущую рабочую версию**. Не следует восстанавливать их при дальнейшей работе без отдельного решения.

## 1. Текущая задача и границы

**Единственная задача текущей версии:** взять полный исходный файл CAIDA AS Relationships `serial-2`, преобразовать AS-отношения в двунаправленное представление типизированных дуг, построить разреженную матрицу CSR и сохранять её в воспроизводимом формате.

Результат — исходный снимок CAIDA и набор файлов `graph.npz`, `edge_types.npy`, `asn_ids.npy`, `metadata.json`. Никакой оптимизации, ранжирования или изменения топологии на этом этапе нет.

**Не реализуем в текущем состоянии:** AS Rank и Customer Cone, PeeringDB/IXP, фильтрацию или ранговый подграф, выбор целевых AS и кандидатов, поиск путей, ACO, метрику DNS, построение визуализаций, отчёты по географии. Прежние целевые ASN и расчёты сокращённого графа не являются параметрами базового CSR-пайплайна.

## 3. Формат входного файла

CAIDA `serial-2`: текстовый `*.as-rel2.txt` или gzip `*.as-rel2.txt.gz`. Строка имеет вид:

```text
asn1|asn2|relationship|source
```

Значения отношений:

- `provider|customer|-1|source` означает provider–customer и преобразуется в две дуги: provider → customer (`DOWNSTREAM = 2`) и customer → provider (`UPSTREAM = 1`).
- `peer1|peer2|0|source` означает peer–peer и преобразуется в две дуги типа `PEER = 3`.

Код обрабатывает пустые строки и комментарии `#`; некорректные ASN, неподдерживаемые типы и петли вызывают ошибку. Повторяющиеся одинаковые дуги устраняются, конфликтующие типы одной направленной пары запрещены. **Четвёртое поле `source` в текущем формате CSR не хранится.** Это сознательное ограничение `csr_aligned_v1`, а не доказательство отсутствия происхождения связи во входном файле.

## 4. Реализация `src/graph.py`

**Основные функции:**

- `open_text(path)` — прозрачное открытие plain text / gzip по расширению.
- `read_relationships(path)` — разбор исходных строк, создание двух направленных дуг на одно отношение и исходных счётчиков строк.
- `build_graph(arcs)` — построение отсортированных `asn_ids`, сопоставление ASN с индексами, сортировка дуг, проверка конфликтов, дедупликация, создание SciPy CSR и выровненного `edge_types`.
- `save_graph(input_file, output_dir)` — сохранение CSR, `edge_types`, `asn_ids`, JSON-метаданных с SHA-256 входного файла.
- `load_graph(directory)` — загрузка сохранённой тройки и проверка совместимости размеров.
- `main()` — CLI с подкомандами `build` и `inspect`.

В минимальной версии `src/graph.py` удалён неиспользуемый helper `make_weighted_graph(...)`: никаких маршрутных весов и оптимизационных вычислений здесь не осталось. Формат CSR при этом не меняется.

### Договор о формате `csr_aligned_v1`

- `graph.npz` — матрица смежности формы `N × N` с ненулевыми значениями `1`, отсортированными индексами CSR.
- `edge_types.npy` — одномерный массив длины `graph.nnz`. **`edge_types[i]` относится к дуге `graph.indices[i]`**, поэтому нельзя независимо сортировать индексы и типы после загрузки.
- `asn_ids.npy` — одномерный строго возрастающий массив ASN длины `N`. Вершина с внутренним индексом `i` соответствует `asn_ids[i]`.
- `metadata.json` — `input_filename`, `input_sha256`, `built_at_utc`, `format`, размеры, счётчики входных отношений и типов дуг.

При дальнейшей реализации не менять эти договорённости молча. При изменении структуры файлов вводить новую версию формата и миграцию.

## 6. Команды воспроизведения

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

python -m src.graph build data/raw/20261101.as-rel2.txt.gz --out data/processed
python -m src.graph inspect --dir data/processed
python -m unittest discover -s tests -v
```

Команда `build` не фильтрует AS и не обращается к AS Rank или PeeringDB. При повторном запуске на том же файле должна воспроизводиться та же топология; поле `built_at_utc` будет обновлено.

### Минимальные проверки корректности

1. `len(asn_ids) == graph.shape[0] == graph.shape[1]`.
2. `len(edge_types) == graph.nnz`.
3. ASN строго возрастают, CSR имеет отсортированные индексы.
4. Типы дуг принадлежат `{1, 2, 3}`; для каждого исходного отношения представлены обе направленные дуги с правильными кодами.
5. Количество дуг равно удвоенному числу уникальных отношений после дедупликации.
6. Метаданные содержат SHA-256 входного снимка; никаких API-зависимостей при сборке нет.
7. Парсер отклоняет конфликтные и повреждённые записи вместо тихого исправления.

Тесты на небольшом фиктивном фрагменте CAIDA не заменяют проверки реального полного снимка.

## 7. Ограничения и честная интерпретация

### Ограничения CAIDA serial-2

1. **Неполнота наблюдений.** BGP-коллекторы Route Views и RIPE RIS получают маршруты от ограниченного числа участников. Таблица одного Tier 1 и даже совокупность таблиц коллекторов не является полным графом Интернета: глобальная достижимость префиксов не означает наблюдаемость всех AS-связей. Private peering может попасть в AS_PATH, но не гарантированно; отсутствие ребра не доказывает отсутствия реального соединения.
2. **Выведенные, а не подтверждённые отношения.** Тип provider–customer или peer определяется алгоритмами CAIDA и может быть неточным. Одна метка на пару AS не учитывает различия BGP-политик по площадке, префиксу, направлению и времени.
3. **`bgp` против `mlp`.** `bgp` — источник вывода об отношении на основе BGP-путей; `mlp` — дополнительная информация о multilateral peering на IX, полученная из сведений о route servers. Нахождение двух AS на одном IX не доказывает наличия peering между ними; `mlp` не обязательно означает отдельную прямую BGP-сессию.
4. **Измерения Ark.** В serial-2 исторически применялись дополнительные выводы из traceroute; новые выводы из Ark перестали добавляться в сентябре 2018 года. Не считать их актуальными трассировками снимка 2026 года.
5. **Эвристики и неполное покрытие.** Классификация отношений и дополнительный вывод связей опираются на эвристики и измерительные точки, которые не покрывают весь Интернет. Результаты зависят от состава наблюдений и даты снимка.

### Ограничения нашей CSR-конверсии

- Граф содержит AS-отношения, **не реальные BGP-таблицы, AS_PATH, данные о маршрутизаторах, PoP, RTT, пропускной способности или объёме трафика**.
- Конверсия представляет каждое отношение двумя направленными дугами, но **не гарантирует**, что произвольный путь по ним допустим реальными BGP-политиками (например, valley-free).
- Исходное поле `source` не сохраняется; после преобразования **нельзя** отделить `bgp` и `mlp` связи, используя только `graph.npz` и `edge_types.npy`. Для этого нужен исходный файл или отдельное расширение формата.
- `graph.npz` хранит `1` как признак соседства, а не стоимость транзита. Никакая оптимизационная функция не утверждена и не применяется.
- Не подменять полную исходную топологию ранее создававшимся подграфом по AS Rank. Текущая базовая версия использует **весь** снимок CAIDA.

## 8. Состояние после pivot

Проект считается приведённым к чистому базовому состоянию, когда в рабочем дереве отсутствуют модули и артефакты прежних экспериментов, установлен минимальный набор зависимостей, команды сборки и проверки выполняются успешно, а README и HANDOFF описывают только актуальное ядро.

**Не следует:** добавлять AS Rank, PeeringDB, ACO или старую модель anycast DNS «заодно». При появлении нового этапа его постановка, критерии качества и изменения формата должны быть согласованы отдельно.
