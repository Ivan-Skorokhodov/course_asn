# Handoff — CAIDA AS-граф, иерархия Интернета и кандидаты для DNS-anycast

## 1. Постановка курсовой (актуальная)

**Задача:** найти топологически выгодные **точки подключения** авторитативного DNS-anycast сервиса к Интернету. ACO выбирает `k` различных AS в качестве сетевых точек подключения, **а не физические серверы по одному на ASN**.

- Одна AS может присутствовать в нескольких городах и дата-центрах.
- Один Anycast-сервис может иметь несколько физических экземпляров и общий анонсируемый префикс.
- Наш граф CAIDA не содержит отдельных PoP, маршрутизаторов, городов, RTT и реальных BGP-политик.
- Выбор `k` AS сам по себе **не гарантирует** ни географической диверсификации, ни возможности договориться о размещении.
- Практический результат ACO в будущем — **ранжированный набор уникальных комбинаций** из `k` AS. Окончательный выбор требует проверки операторов и площадок человеком. Простое сложение top-k лучших одиночных AS некорректно из-за перекрытия зон улучшения.

### Математическая модель (пока без географии)

`G=(V,E)` — весь ориентированный AS-граф; `S` — Source AS; `D` — существующие сетевые точки подключения DNS; `C` — кандидаты; `q_s` — условный или измеренный вес DNS-трафика; `X⊆C`, `|X|=k`.

Стоимость дуги `w(u,v)=1+α` для customer→provider (upstream), иначе `1`, `α≥0`. `Hα(s,c)` — минимальная сумма этих весов по пути из `s` в `c`. Базовая стоимость `h⁰_s=min_{d∈D} Hα(s,d)`.

`B(X)=Σ_{s∈S} q_s [h⁰_s − min(h⁰_s, min_{c∈X}Hα(s,c))] → max`.

Маршруты — **приближение по AS-графу**, не симуляция Anycast/BGP. Параметр `α` меняет модельную стоимость маршрутов, а не размещение физических серверов.

## 2. Почему CSR

- Граф разреженный: ~680 тыс. отношений дают ~1,36 млн направленных дуг.
- CSR (`indptr`, `indices`) позволяет быстро получать соседей и подходит для расчёта кратчайших путей SciPy.
- `edge_types.npy` хранит типы дуг **по тем же индексам**, что `graph.indices`. Можно менять веса при изменении `α` без перестройки связности.
- Плотная матрица смежности `O(|V|²)` не нужна; NetworkX удобнее оставлять для маленьких отладочных примеров; графовая СУБД избыточна.

| Подход | Плюсы | Минусы | Решение |
|---|---|---|---|
| CSR (SciPy/NumPy) | Компактность, быстрые численные алгоритмы | Неудобна частая модификация | **Основной формат** |
| Списки смежности | Легко изменять | Python-накладные расходы | Для прототипов |
| NetworkX | Простой API | Память и скорость на большом графе | Для небольших подграфов |
| Плотная матрица | Прямой доступ к любой паре | `O(|V|²)` памяти | Нет |
| Графовая СУБД | Удобные запросы | Дополнительная инфраструктура | Нет |

### Исходные данные

CAIDA `serial-2`, `*.as-rel2.txt[.gz]`:

- `provider|customer|-1|source` → `provider→customer` (`downstream=2`) и `customer→provider` (`upstream=1`);
- `peer|peer|0|source` → двунаправленные `peer=3`.

Повторяющиеся одинаковые дуги удаляются, противоречивые отношения вызывают ошибку. Поле provenance `source` не сохраняется.

`data/processed/`:
- `graph.npz` — CSR со значениями `data=1`;
- `edge_types.npy` — коды дуг, выровненные по CSR;
- `asn_ids.npy` — отображение внутренних индексов в ASN;
- `metadata.json` — размер, имя и SHA-256 исходного снимка.

### Построение и проверка

```bash
python -m pip install -r requirements.txt
python -m src.graph build data/raw/20261101.as-rel2.txt.gz --out data/processed
python -m src.graph inspect --dir data/processed
python -m unittest discover -s tests -v
```

Исходный CAIDA TXT пользователь размещает в `data/raw/` сам. Граф **всегда остаётся полным** для маршрутизации и ACO.

## 3. Исследование иерархии AS (новый этап)

Сначала анализируем реальные отношения AS сверху вниз, **не запускаем ACO**.

`src/as_analysis.py` реализует:

1. Подсчёт степеней **всех** AS по CSR: прямые клиенты, провайдеры, peers, общее число соседей.
2. Опциональное дополнение метрик верхними AS по опубликованным `rank` и `customer_cone` через **CAIDA AS Rank GraphQL API**. Неполученные значения остаются пустыми; степень клиентов **не подменяется** Customer Cone.
3. Предварительный список кандидатов из пересекающихся групп `large_cone`, `middle_cone`, `high_peering`. Без данных AS Rank честно используются `high_customer_degree` / `middle_customer_degree` как эвристики.
4. Команду `hierarchy` для небольшого дерева из **только provider→customer** связей. Оно показывает, как ветви распространяются от выбранной AS; при мультихоминге и ограничении узлов это лишь дерево первого обнаружения, **не полный Customer Cone**.

Топологически крупная AS не обязательно географически глобальная. `large_cone` и `middle_cone` — **технические группы ранжирования**, а не проверенные классы глобальных/региональных операторов. `peer_degree` из CAIDA serial-2 — оценочная характеристика, особенно осторожно интерпретировать multilateral peering.

### Три CSV

Файлы генерируются в `data/analysis/` и не содержат вымышленных реальных данных.

| Файл | Что содержит | Источник |
|---|---|---|
| `as_metrics.csv` | Все ASN, `customer_degree`, `provider_degree`, `peer_degree`, `total_degree`; для совпавшей части — `asrank_rank`, `asrank_cone_asns`, имя и организация | CAIDA CSR + опционально CAIDA AS Rank |
| `candidates.csv` | Уникальные отобранные ASN; `groups` может содержать несколько групп через `\|`; показатели и (после обогащения) число площадок/IX, страны и отдельно города facilities и IX | Отбор по `as_metrics.csv` + `asn_sites.csv` |
| `asn_sites.csv` | Одна строка на (ASN, facility) или (ASN, IX); ID, название, город, страна, координаты facility и ссылка | PeeringDB |

Пример запуска из корня репозитория:

```bash
# Вычисление степеней всех AS и, при доступном интернете, top-500 по AS Rank
python -m src.as_analysis metrics --asrank-top 500

# Начальный список без географии
python -m src.as_analysis candidates --large 40 --middle 80 --peering 80

# Просмотр ветви клиентской иерархии
python -m src.as_analysis hierarchy --as 3356 --depth 2 --max-nodes 60

# Дополнение площадками выбранных AS (запросы PeeringDB)
python -m src.peeringdb_sites

# Повторно сформировать candidates.csv с числом мест присутствия
python -m src.as_analysis candidates --sites data/analysis/asn_sites.csv
```

Если нет интернета, `metrics` можно выполнить **без** `--asrank-top`: тогда рейтинг кандидатов строится по числу **прямых** клиентов, поля AS Rank пустые. Работа с PeeringDB требует сеть; никаких фиктивных географических строк код не создаёт.

### PeeringDB: тонкости и ограничения

Используем разные сущности:

- `net` (ASN) → `netfac` → `fac` — заявленное присутствие сети в **конкретном физическом дата-центре**. Для `facility` сохраняем его город и координаты, `location_scope=facility_presence`.
- `net` → `netixlan` → `ix` — участие AS в **IX**. Город IX — **город регистрации/описания точки обмена, а не доказательство местонахождения оборудования сети**: возможен remote peering и распределённые IX. Координаты для строк IX оставляем пустыми, `location_scope=ix_registered_city_not_verified_pop`.
- Наличие записи в PeeringDB **не означает** возможности разместить DNS там без договора. Отсутствие записи **не доказывает** отсутствие физического присутствия.
- Поле `countries` сводит оба типа данных. Для физической географии анализировать `facility_cities`, `facility_countries`, а `ix_registered_cities` считать лишь дополнительной справочной информацией.

Для экономии запросов PeeringDB запросы группируются через `__in` (пакеты по 100), используется локальный кэш `data/analysis/.cache/`, интервал не меньше 3.1 с между запросами, а при наличии `PEERINGDB_API_KEY` применяется ключ. Параметр `--refresh` принудительно обновляет кэш; обновлённый клиент также поддерживает `--timeout`, `--retries`, `--limit-asns`. Для больших масштабов позже предпочтительна локальная реплика `peeringdb-py`.

**Воспроизводимость:** CSR относится к фиксированной дате, тогда как AS Rank/PeeringDB предоставляют более поздние актуальные данные. Для строгого исследования надо сохранять дату получения, копию кэша и явно описывать несовпадение временных срезов. `asn_sites.csv` содержит `exported_utc` (время создания CSV, **не обязательно время сетевого запроса**); кэш не следует автоматически считать актуальным.

На пользовательской машине завершён полный цикл `metrics → candidates → PeeringDB → candidates --sites`:

Эти числа — **наблюдение локального запуска**, а не гарантированные результаты для другого снимка CAIDA или другой даты PeeringDB. Данные не проверялись вручную на уникальность географических мест: число строк включает отдельные записи о присутствии AS в facility и IX. Наличие площадки не равно возможности развернуть DNS без дополнительных договорённостей.

**Единая инструкция по выполнению команд и исследованию результатов находится в `README.md`, разделы 1–4.** В ней есть полный порядок, пример просмотра top-AS, `hierarchy`, BFS-визуализация и осторожная проверка PeeringDB. Пробный запуск `--limit-asns 5` должен использовать `--out data/analysis/asn_sites_sample.csv`, чтобы не затереть полный файл.

Следующее практическое действие: вручную сравнить лидеров по `asrank_cone_asns`, `peer_degree` и географическому присутствию (`facility_countries`, `facility_cities`), затем сформировать осмысленные `S` и `D`. **ACO пока не реализуем** — сначала нужны определения исходного распределения DNS и целевой метрики.

## 4. План дальнейшей работы: AS Rank → ACO → экспертная проверка

Зафиксированный исследовательский процесс:

1. **AS Rank + полный CAIDA CSR.** Выделить топологически значимые AS, крупную клиентскую иерархию и сети с большим числом peers; сравнить ранги, Customer Cone и степень peer. Исследовать IX-сообщества отдельно: IX — не ASN и не означает, что все участники имеют peering друг с другом.
2. **Формирование `C`.** Использовать смесь крупных, средних и активно пиринговых AS. Не ограничивать кандидатов только top-10 AS Rank; сохранять возможность отдельного анализа региональных операторов после географического обогащения.
3. **Сформировать `S`, `D`, `q_s`, `k`, `α`.** `D` — существующие сетевые точки подключения, не отдельные physical PoP. Не приписывать источникам реальный объём DNS без измерений.
4. **Матрица маршрутов.** Взвешенный CSR, кратчайшие пути `Hα`, базовые `h⁰_s`, матрица улучшений `A_sc=max(0,h⁰_s-Hα(s,c))`. Исходный полный граф, без `--edge-cutoff` и без BFS-дерева визуализации.
5. **ACO.** Муравьи выбирают комбинации ровно `k` **различных AS**. Сохранять top-N уникальных наборов, `B(X)`, время, стабильность по seed. Отдельно рейтинг одиночных AS для интерпретации, но **не** считать top-k одиночных лучшим набором.
6. **Контроль качества.** Greedy / Lazy Greedy, малые случаи полным перебором; использовать сопоставимые бюджеты вычислений.
7. **PeeringDB + экспертная проверка.** Для лучших наборов оценивать наличие площадок, географическую диверсификацию, договорную доступность и практическую стоимость. Невозможные кандидаты можно исключить и запустить оптимизацию повторно.
8. **Будущее расширение, не базовая версия.** При необходимости менять единицу оптимизации с ASN на `(ASN, площадка)` и добавлять географические ограничения/RTT. Но AS-level расстояния `Hα(s,ASN)` не могут различить две площадки одной AS; для этого нужны независимые измерения, например RIPE Atlas.

**Центральный исследовательский вопрос:** насколько высокий CAIDA AS Rank/Customer Cone коррелирует с выгодой кандидата как точки подключения DNS-anycast, и помогают ли более региональные или peer-ориентированные AS улучшить решение?

### Важные ограничения

- Inferred CAIDA relationships, упрощённые shortest paths, отсутствие настоящей BGP-policy, latency и трафика.
- Topological rank ≠ DNS-оптимальность ≠ коммерческая доступность площадки.
- Подграф/дерево BFS из `graph_neighbors.py` — исключительно инструмент изучения; `--edge-cutoff` пропускает ветви прямо во время обхода и **не должен** применяться к алгоритму оптимизации.
- Географическая дисперсия не обеспечивается без дополнительного ограничения; ASN не является однозначной географической точкой.
